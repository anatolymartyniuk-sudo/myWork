РАННИЙ ПЕРИОД (этапы 1-28): PowerShell-скрипт usb_block.ps1
============================================================
Запасной инструмент: usb_block.ps1 с меню:
  1 Заблокировать (кроме whitelist), 2 Разблокировать всё USB,
  3 Сканировать и добавить устройства, 4 Обновить правила (+доустановка
  драйверов), 5 Очистить следы USB-накопителей (+ВСЕ из ветки
  "Переносные устройства"), 0 Выход; автоматический режим: -ApplyOnly.

Механика: политика DeviceInstall\Restrictions (DenyUnspecified=1).
В AllowDeviceIDs попадают HardwareID из whitelist + базовые HID-записи
(USB\Class_03, HID_DEVICE), чтобы мыши/клавиатуры продолжали работать.

Ключевой вывод: USB-накопитель — это дерево узлов (USB-узел VID/PID +
USBSTOR-узел диска + том STORAGE\VOLUME). Драйвер диска USBSTOR
добавляется автоматически ТОЛЬКО для подключённых устройств; для
ранее не подключавшихся whitelist-устройств нужен один запуск пункта 4.

Ограничение политики: DenyUnspecified блокирует ТОЛЬКО установку
драйверов НОВЫХ устройств. Уже установленный драйвер политика не
отключает — это ключевое ограничение, из-за которого выбрана другая
механика для основного инструмента (exe).

Кодировки (актуально и для exe): cmd/Readme/HISTORY — UTF-8 без BOM;
ps1/whitelist.txt — UTF-8 BOM (требование PowerShell 5.1 для русского
текста).

Переход на exe (этап 29): вместо установки драйверов выбрано снятие
буквы тома (mountvol <буква>: /p) — накопитель распознаётся Windows,
но не получает букву и остаётся недоступным. exe в трее стал
основным инструментом, ps1 — запасным.

--------------------------------------------------
ЭТАП 29. WHITELIST - БЛОКИ USB+ID+SN+SWD (В РАБОТЕ); РЕШЕНО ДЕЛАТЬ EXE
--------------------------------------------------
Пользователь: "поменяй структуру файла whitelist, заноси в него ID, SWD и SN
разрешённого usb-накопителя. на основе этих данных, если все совпадают,
оборудование должно быть доступно".

Новый формат whitelist.txt - ОДИН БЛОК НА НАКОПИТЕЛЬ из полей:
  USB=USB\VID_xxxx&PID_xxxx     ID USB-узла (разрешает узел)
  ID =USBSTOR\Disk…             конкретный HardwareID диска (модель)
  SN =081NS9HV47JMZLUQ&0        серийный номер накопителя
  SWD=SWD\WPDBUSENUM\…          WPD-узел ("Переносное устройство")
Устройство считается разрешённым ТОЛЬКО при совпадении ВСЕХ полей.
Реальные данные референса (живая система, JetFlash):
  ID =USBSTOR\DiskJetFlashTranscend_8GB___1100
  SN =081NS9HV47JMZLUQ&0
  SWD=SWD\WPDBUSENUM\_??_USBSTOR#DISK&VEN_JETFLASH&PROD_TRANSCEND_8GB&REV_1100#081NS9HV47JMZLUQ&0#{53F56307-B6BF-11D0-94F2-00A0C91EFB8B}
  WPD-узел имеет COMP: wpdbusenum\fs | SWD\Generic (серийник - в пути узла).

Сделано в usb_block.ps1 (этап 29, начато):
1. Новые функции: Read-Whitelist (блочный парсер), Get-SerialRoot,
   Get-UsbVidPidBySerial, Get-WpdBySerial, Test-BlockMatch.
2. Update-AllowList переписан: разрешения СТРОГО из блоков whitelist (USB
   узел + ID диска + STORAGE\VOLUME, если есть диск; + базовые HID-записи
   Class_03/HID_DEVICE). Никакого перечисления подключённых устройств.
   Итого в политике появляются конкретные идентификаторы, а не всё подряд.
3. Disconnect-Unauthorized: разрешает накопитель, только если блок совпал
   по USB+ID+SN+SWD (неполный блок - предупреждение, включается по USB,
   просит дописать ID/SN/SWD).
4. Show-Devices: печатает готовые строки USB=/ID=/SN=/SWD= для ручной
   записи в whitelist.txt.

НЕ ДОДЕЛАНО (пауза, этап 29 продолжаем в следующей сессии):
- Add-ConnectedToWhitelist (пункт 3) всё ещё пишет в whitelist голые

ЭТАП 31. КОПИИ EXE ПРИ КАЖДОМ ЗАПУСКЕ (PROGRAM FILES + PROGRAMDATA\MAA)
--------------------------------------------------
Запрос пользователя: "добавь перемещение защищённой копии исполняемого
файла и в C:\ProgramData\MAA, при отсутствии папки создай её".

Состояние: копия в ProgramData\MAA уже была реализована в
ProtectedCopy.EnsureInstalledCopy() (MaaDir = %ProgramData%\MAA,
MaaExe = usb_block_tray.exe, папка создаётся Directory.CreateDirectory,
ACL такой же, как у Program Files\USB_Block), но вызывалась ТОЛЬКО при:
  * --makecopies;
  * включении автозапуска (AutoStart.Set(true));
  * установке службы (ServiceManager.Install).
При обычном запуске трея копии могли устаревать.

Решение:
- В Program.Main после проверки прав администратора (и до создания
  mutex/трея) добавлен вызов ProtectedCopy.EnsureInstalledCopy().
  Теперь при КАЖДОМ запуске под админом обе защищённые копии
  (Program Files\USB_Block и C:\ProgramData\MAA) обновляются из
  текущего exe, папка ProgramData\MAA создаётся при отсутствии.
- Если запуск уже идёт из защищённой копии - она просто повторно
  копирует себя в обе папки (конструктивно безвредно).

Проверено: пересборка csc (Framework 64 v4.0.30319, target=winexe):
без ошибок; usb_block_tray.exe обновлён (64512 байт).
Примечание об компиляции: в Git Bash аргументы вида /r:... подменяются
на пути, поэтому используются -r: (с дефисом).

ЭТАП 33. ПУНКТ 2 "РАЗБЛОКИРОВАТЬ" НЕ ВОЗВРАЩАЛ БУКВУ ДИСКА
--------------------------------------------------
Пользователь: "пункт 1 Заблокировать работает, пункт 2 Разблокировать
не работает - usb-устройство, которое было заблокировано, после
разблокировки не монтируется".

Причина (по справке mountvol):
- Блокировка делала mountvol X: /p. Опция /p "удаляет точку подключения,
  отключает том и ПЕРЕВОДИТ ТОМ В НЕПОДКЛЮЧАЕМОЕ СОСТОЯНИЕ. Том можно
  сделать подключаемым, заново создав точку подключения тома".
- Разблокировка делала только mountvol /r, а /r "удаляет папки и
  параметры реестра точек подключения тома для томов, которые БОЛЬШЕ
  НЕ СУЩЕСТВУЮТ" - т.е. /r НЕ возвращает точки подключения
  существующих (отключённых через /p) томов. Поэтому после
  "Разблокировать" буква не возвращалась.

Решение (внесено в usb_block_tray.cs, класс MountUtil):
- Перед снятием буквы запоминается путь тома: GetVolumePath(letter)
  через "mountvol <буква>:\\ /L" -> "\\?\Volume{GUID}\" (учтён нюанс:
  /L требует форму <буква>:\, а не <буква>:).
- Пары буква->GUID пишутся в реестр
  HKLM\SOFTWARE\USB_Block\UnmountedVolumes (Track()).
- RestoreUnmounted(): для каждой сохранённой записи подбирает свободную
  букву (предпочтительно исходную, FreeLetter()) и заново создаёт точку
  подключения: "mountvol <буква>: \\?\Volume{GUID}\" (Remount()).
- RestoreUnmounted() вызывается при: пункт 2 Разблокировать, добавлении
  устройства (пункт 3), импорте whitelist (пункт 5), удалении программы
  (пункт 9) - всюду, где раньше был только RestoreAll().
- ClearTrack() - очистка учёта (на будущее).

Ограничение: тома, которые залипли под СТАРОЙ версией (до этого фикса),
в реестре не отмечены - их возврат вручную (Управление дисками) или
переподключением накопителя. Новые блокировки восстановимы пунктом 2.

Проверено:

ЭТАП 35. КНОПКА "ДОБАВИТЬ" НЕАКТИВНА (ДВЕ ОШИБКИ В UsbQuery)
--------------------------------------------------
Пользователь: "не могу добавить usb-устройство в whitelist, кнопка
«Добавить» неактивна".

Диагностика (--diag на живой системе с подключённым JetFlash):
- USB-диск находился, но в строке было "USB=" ПУСТО (и VIDPID=USB).
- Кнопка "Добавить" в AddDeviceDialog активируется только если у устройства
  заполнен UsbId/Serial; при пустом UsbId накопитель также молча
  отбрасывается в DoAddDevice.

Причины (обе - в классе UsbQuery, usb_block_tray.cs):
1. FindUsbIdBySerial и GetUsbMassStorageNodes использовали WQL-запрос
   "SELECT * FROM Win32_PnPEntity WHERE DeviceID LIKE 'USB\%'".
   В WQL обратный слэш - служебный символ экранирования, поэтому такой
   запрос некорректен и выбрасывает исключение; оно глушилось catch, и
   функция всегда возвращала null/пусто. Проверено отдельным тестом
   (wmitest.cs): 'LIKE USB\%' - ошибка; 'LIKE USB%' и без WHERE - работают.
2. NormalizeVidPid разрезал id по ПЕРВОМУ обратному слэшу:
   для "USB\VID_8564&PID_1000" head = "USB", далее split по '&' давал один
   элемент - на выходе "USB". ExtractVidPid дополнительно обрезал
   instanceId до первого '\' и передавал в NormalizeVidPid голое "USB".
   (В ps1-версии то же самое делал regex ^USB\(VID_..)&(PID_..).)

Исправления:
- Оба запроса заменены на "SELECT * FROM Win32_PnPEntity" без WHERE;
  фильтрация по префиксу "USB\" выполняется в коде (FindUsbIdBySerial),
  StartWith("USB\VID_") уже был (GetUsbMassStorageNodes).
- FindUsbIdBySerial дополнен fallback-проходом по реестру
  (GetAllMassStorageInstances): находит USB\VID_..&PID_..\SN даже для
  НЕподключённого (заблокированного/снятого) накопителя - нужно функции
  BuildAddDeviceList (этап 34).
- NormalizeVidPid переписан: ищет "VID_", берёт VID_xxxx и PID_yyyy,
  отбрасывая \серийник, &MI_xx, &REV_xx; возвращает
  "USB\VID_xxxx&PID_yyyy" в верхнем регистре (как в ps1).
- ExtractVidPid теперь просто вызывает NormalizeVidPid(instanceId).

Проверено: csc без ошибок; --diag показывает
  USB=USB\VID_8564&PID_1000  SN=081NS9HV47JMZLUQ  DISKID=USBSTOR\DiskJetFlash...
  для подключённого JetFlash; "USB-узлы массовой памяти: Найдено: 1"

ЭТАП 41. АВТОЗАПУСК БЕЗ ЗАПРОСА UAC (ПЛАНИРОВЩИК ЗАДАЧ)
--------------------------------------------------
Пользователь: "при добавлении программы в автозагрузку, после
перезагрузки программа запрашивает права администратора для внесения

Причина: автозапуск был записью в HKLM\...\Run, которая запускает
программу НЕ повышено; Program.Main при запуске не-админом перезапускал
себя через Start-Process -Verb RunAs -> на каждый вход в систему при
старте из автозапуска появлялся запрос UAC.

Выбор пользователя: "Планировщик задач" - автозапуск через задачу
в Планировщике с "Наивысшими правами". Задачи, созданные с RunLevel
Highest, при входе в систему запускаются службой планировщика молча,
с полными правами и БЕЗ запроса UAC.

Сделано в usb_block_tray.cs (класс AutoStart):
- Автозапуск переведён со Run-ключа на задачу Планировщика:
    schtasks /Create /TN "USB_Block_Tray"
              /TR "\"C:\Program Files\USB_Block\usb_block_tray.exe\""
              /SC ONLOGON /RL HIGHEST /F
  (запуск при входе, с наивысшими правами, без UAC-запроса).
- Set(true) сначала обновляет защищённую копию (EnsureInstalledCopy),
  затем создаёт задачу; Set(false) - schtasks /Delete /F.
- Старый Run-ключ при включении/выключении автозапуска удаляется
  (иначе останется двойной запуск и запрос UAC). Перегрузка с
  ProcessStartInfo (UseShellExecute=false) передаёт аргументы без
  подмены путей, поэтому используется Exec.Run("schtasks.exe", ...).
- IsEnabled(): true, если есть задача ИЛИ остался старый Run-ключ
  (обратная совместимость со старыми установками).
- MigrateRunToTask(): при каждом старте с правами администратора
  (Program.Main, после EnsureInstalledCopy) переводит уже настроенный
  старый Run-ключ на задачу - пользователю не нужно ничего перенастраивать.
- Единственный Mutex исключает двойной запуск (задача + ручной запуск).

ПРИЧИНА (найдена и воспроизведена локально):
- Неверное значение <RunLevel> в XML задачи: было "Highest". В XML-схеме
  Task Scheduler (runLevelType simple type) допустимы ТОЛЬКО значения
  "LeastPrivilege" и "HighestAvailable". Имена "Limited"/"Highest" - это
  значения перечисления PowerShell (New-ScheduledTaskPrincipal -RunLevel)
  и целочисленных констант TASK_RUNLEVEL_*, они НЕ валидны в XML.
  schtasks при этом выдаёт ровно "out of range" (позиция ошибки указывает
  на элемент <RunLevel>).
- Воспроизведено тестом через COM (Schedule.Service):
  * <RunLevel>Limited</RunLevel> или <RunLevel>Highest</RunLevel> ->
    ошибка валидации с позицией (..):RunLevel:...;
  * <RunLevel>LeastPrivilege</RunLevel> -> задача регистрируется;
  * <RunLevel>HighestAvailable</RunLevel> + GroupId + LogonTrigger +
    полные Settings -> единственная ошибка у не-администратора - обычный
    "Отказано в доступе" (0x80070005), т.е. XML валиден, не хватает прав
    (для администратора право есть, задача создастся).
- Кодировка файла XML (UTF-16 LE с BOM) - корректна: schtasks принимает
  UTF-16LE и ANSI.

Исправление в usb_block_tray.cs (TrayTask.BuildXml):
  <RunLevel>Highest</RunLevel>  ->  <RunLevel>HighestAvailable</RunLevel>

Прочие проблемы после этого уходят сами: задача создаётся -> после
перезагрузки у каждого пользователя запускается трей (--logon) -> он
читает очередь HKLM\SOFTWARE\USB_Block\Events и показывает уведомления.

ЭТАП 47. УВЕДОМЛЕНИЯ НЕ ЗАВИСЯТ ОТ ВЫГРУЗКИ ТРЕЯ (ОТДЕЛЬНЫЙ
         ПРОЦЕСС-УВЕДОМИТЕЛЬ --notify)
--------------------------------------------------
Запрос пользователя: не-админ может выгрузить программу из трея ("Выход")
и после этого перестаёт получать сообщения о блокировках. Возможность
выгрузки оставить, но сообщения пользователь должен получать в любом
случае.

Решение: уведомления ВЫНЕСЕНЫ ИЗ ТРЕЯ в отдельный скрытый процесс-
уведомитель, который живёт сам по себе:
- Трей (--logon) больше НЕ показывает уведомления и НЕ опрашивает очередь
  событий: он занимается только блокировкой (под администратором), статусом
  и управлением. Его "Выход" влияет только на сам трей.
- Уведомитель (--notify): невидимый процесс БЕЗ трея, без меню и без
  элементов интерфейса. Запускается задачей "USB_Block_Notify_Logon" при
  входе каждого пользователя, раз в 2,5 с читает общую очередь
  HKLM\SOFTWARE\USB_Block\Events и показывает вновь появившиеся события
  всплывающими окнами (NotifyPopup - без рамки, справа внизу, поверх окон,
  автозакрытие 6 с, очередь событий показываются по одному в столбик).
  Уведомитель нечем "выгрузить" (в системной области его нет), поэтому
  после выгрузки трея сообщения продолжают приходить.
- Взаимодействие: общий счётчик HKCU Software\USB_Block\LastEventId один
  (последнее показанное событие); трей его больше не трогает, единственный
  читатель/писатель - уведомитель, поэтому дублей нет.
- Один экземпляр уведомителя на сессию: мьютекс
  Local\UsbBlockNotify_SingleInstance_v2.

Изменения в usb_block_tray.cs:
- Program.Main: флаг --notify / -notify; до проверки прав выполняется
  ветка: мьютекс уведомителя -> NotifyService.Run() -> выход (без
  повышения прав, без копий, без трея).
- Класс NotifyService: таймер-поллер очереди + очередь сообщений +
  показ по одному NotifyPopup. Помещает окна снизу вверх с отступом.
- Класс NotifyPopup: Form без рамки, атрибуты TopMost + ShowInTaskbar
  false, размер через TextRenderer (работает до отрисовки), автозакрытие.
- TrayContext: TickScan() теперь только RunScan() для администратора;
  методы PollAndNotify()/NotifyEvent() удалены (уведомления ушли в
  NotifyService). Text подсказки меню 7 уточнён.
- TrayTask: две задачи при установке службы:
    USB_Block_Tray_Logon   (--logon)   - значок в трее;
    USB_Block_Notify_Logon (--notify)  - скрытый уведомитель.
  Create() создаёт обе (ошибки по каждой выводятся отдельно текстом
  schtasks с позицией элемента). Delete() удаляет обе. XML задачи
  параметризован аргументом (BuildXml(args)).
- Ограничение (осталось заказчику): процесс уведомителя можно убить через
  Диспетчер задач, но штатным интерфейсом программы (трей/меню) его
  завершить нельзя; после перезагрузки он снова стартует задачей.

Проверено:
- csc (Framework 64 v4.0.30319, winexe, -win32icon) без ошибок;
- exe пересобран, трейлер USBICON на месте; --selftest 7/7 OK; --diag OK;
- --notify запущен в сессии без прав администратора: процесс стартует и
  живёт (проверено, затем завершён);
- --logon и обычный запуск трея не конфликтуют с -notify (мьютексы разные).
- Пользователю: выполняет меню 8 -> 7 (пересоздание обеих задач), после
  перезагрузки проверяет: выгрузить трей у не-админа, затем подождать

Причина 1 (порядок в службе). UsbBlockService.OnTick сначала вызывал
EventLog.WriteEntry(...) и только затем NotifyStore.Write(...). Источник
журнала "UsbBlockMonitor" при установке службы через WMI
(Win32_Service.Create) НЕ регистрируется. Проверка на этой машине:
EventLog.WriteEntry с незарегистрированным источником бросает исключение
("...источник не найден, но не удалось выполнить поиск... Недоступные
журналы: Security, State"). Исключение попадало в общий catch, строка
NotifyStore.Write НЕ ВЫПОЛНЯЛАСЬ: том снимался (блокировка работала), а
событие в очередь не писалось. Трей обычно не успевал (служба сканирует
каждые 2 с, трей - 3 с) и тоже не писал. Итог: очередь пуста -> уведомлений
нет ни у кого.
Исправление: в OnTick сначала NotifyStore.Write, затем EventLog.WriteEntry в
ОТДЕЛЬНОМ try/catch (недоступный журнал больше не срывает уведомление).

Причина 2 (условие записи). UsbMonitor.Scan добавлял накопитель в список
"вновь заблокированных" только если MountUtil.Unmount() вернул true (код
возврата mountvol = 0). Если буква фактически снималась, но код возврата был
ненулевым, либо том уже снял параллельно трей/служба, событие не писалось,
хотя блокировка срабатывала.
Исправление: Scan зовёт MountUtil.Unmount(v) и ВСЕГДА добавляет посторонний
накопитель. Успешно снятый том исчезает из UsbQuery.GetUsbVolumes (нет точки
монтирования) и повторно не попадает; повторы для неубранного тома гасит
дедупликация NotifyStore.Write (окно 30 с). Иных потребителей списка, кроме
показа уведомлений, нет.

Дополнительно (изоляция и диагностика):
- TrayContext.TickScan: показ (NotifyService.PollCore) обёрнут в собственный
  try/catch - сбой показа не должен мешать RunScan (блокировке и записи).
- Diag: строки "Источник журнала событий (UsbBlockMonitor)" и "Запись в
  очередь (HKLM\...\Events)" (QueueWriteTest создаёт и сразу удаляет
  служебное значение - ложных уведомлений не даёт). Сразу видно, может ли
  процесс писать в очередь и зарегистрирован ли источник.

Проверено: csc без ошибок; exe пересобран, трейлер USBICON на месте;
--selftest 7/7 OK; --diag выводит новые строки (не-админ: запись в очередь
"НЕТ (Отказано в доступе)" - ожидаемо; чтение очереди работает).
Сквозную проверку под администратором выполнить не удалось (нужен ручной
клик в UAC) - проверить на целевой машине, запустив --diag после подключения
блокируемого накопителя.

ЭТАП 54. УВЕДОМЛЕНИЯ НЕ ПРИХОДЯТ, ХОТЯ ЗАПИСЬ РАБОТАЕТ: СЧЁТЧИК
         ПРОДВИГАЛСЯ РАНЬШЕ ПОКАЗА, ПРИ СБОЕ ОКНА СОБЫТИЕ ТЕРЯЛОСЬ
--------------------------------------------------
Жалоба (Windows 10): служба установлена, блокировка включена, после
перезагрузки при подключении постороннего USB-накопителя сообщений не
получает НИ администратор, НИ обычный пользователь, хотя блокировка
работает. Диагностика на целевой машине:
- Служба установлена, обе задачи Планировщика есть, уведомитель работает,
  whitelist читается, блокировка активна.
- Очередь (HKLM\SOFTWARE\USB_Block\Events): "записей=1, макс.id=1,
  LastEventId(HKCU)=1" - т.е. событие было ЗАПИСАНО и уже прочитано, но не

- Решающий тест: --diag до подключения накопителя, затем подключить,

Значит, цепочка "запись -> чтение" исправна, сломан ПОКАЗ.

Причина (в коде). NotifyService.PollCore() вызывал
NotifyStore.SetLastSeen(max) ДО ShowNext(). Ошибка в создании/показе окна
(например, отсутствие контекста рабочего стола, сбой отрисовки - точно не

"показанным". Событие терялось НАВСЕГДА: все последующие опросы пропускали
его (id меньше/равен LastEventId), и ни трей, ни уведомитель, ни перезапуск
не могли его показать. Любое новое событие "съедалось" так же. Отсюда
"никто ничего не получает" при здоровых службе, задачах и очереди.

Исправление:
- LastEventId продвигается ТОЛЬКО после фактического показа: у NotifyPopup
  добавлено событие Displayed, вызываемое в OnShown (окно реально видимо);
  NotifyService подписывается и делает SetLastSeen(показанный id). Пока окно
  не показано, событие ОСТАЁТСЯ в очереди показа и будет повторено на
  следующем такте - потеря исключена.
- ShowNext(): создание окна в своём try/catch (ошибка конструирования не
  снимает событие с очереди; запоминается LastShowError), вызов Show() тоже
  с перехватом. NofityPopup.NotificationId - номер события, выводимого окном
  (для тестового окна -1, счётчик не трогается).
- Очередь показа хранит (id, текст) - код счётчика привязан к id события.
- Самопроверка: "--testpopup" - показывает тестовое окно-уведомление на 8 с.
  Запускается под администратором и без прав: сразу видно, умеет ли машина
  показывать всплывающие окна вообще.
- Лог-след показа: %TEMP%\usb_block_notify.log (кольцо ~200 строк) - приход
  новых событий, попытки показать, ошибки, фактический показ. --diag выводит
  его хвост "Лог показа уведомлений". По логу видно, доходил ли показ на
  целевой машине и почему падал.

Проверено: csc без ошибок; exe пересобран, трейлер USBICON на месте;
--selftest 7/7 OK; --diag выводит новую строку "Лог показа уведомлений";
--testpopup отработал (окно закрылось само, выход 0).
Дальше: проверить на целевой машине Windows 10 - обновить защищённую копию,

ЭТАП 56. НЕ-АДМИН НЕ ПОЛУЧАЕТ СООБЩЕНИЙ: СЧЁТЧИК LastEventId БЫЛ

  (last=N > max=M): извлекаю последнее событие id=...".
- Для нормального случая новых событий (last<max) поведение прежнее:
  показываются все id>last.

ЭТАП 61. УВЕДОМЛЕНИЕ О ПРИСУТСТВУЮЩЕМ ПОСТОРОННЕМ ДИСКЕ 
       БЕЗ БУКВЫ (И ПОСЛЕ РЕБУТА)
--------------------------------------------------
Жалоба после этапа 60: сообщение приходит ТОЛЬКО при ПЕРВОМ блокировании
постороннего устройства, а блокированного накопителя, уже подключённого
к ОС (например, присутствующего при загрузке), уведомления нет вообще.

Причина: детект блокировки построен на скане смонтированных томов С
БУКВОЙ (GetUsbVolumes -> Win32_LogicalDisk). Если том был размонтирован
нашими же mountvol /D, то на перезагрузке он остаётся висеть на системном
точке монтирования \??\Volume{GUID}, новую букву не получает, и скан его
не видит: блокировка есть, событие не пишется, сообщения нет.

Решение (UsbQuery.GetUsbDisksWithNoLetter + UsbMonitor):
- новый запрос внёсся по цепочке Win32_DiskDrive(USB) -> DiskIndex ->
  Win32_DiskPartition -> Win32_LogicalDiskToPartition: вычисляются диски,
  у которых есть разделы, но НИ ОДИН раздел не смонтирован буквой;
- для таких дисков Scan формирует BlockedDevice как для обычного тома
(если диск не в whitelist) - событие пишется в очередь, уведомление
  доходит;
- повторный спам исключён: статический _reportedLetterless (per-процесс)
  - одно уведомление на физическое присутствие диска; снимается ключ при
  исчезновении диска, а сразу после снятия буквы с обычного тома ключ
  диска заносится в набор, чтобы не задвоить уведомление;
- статус "без буквы" не приравнивается к реально отсутствующему и не
  пересекается с обычным путём (диск с буквой обрабатывается как раньше).

Проверено: csc без ошибок; exe пересобран с трейлером; selftest 7/7 OK.
Развёртывание на целевой машине: запустить новую сборку от АДМИНА один
раз (самоустановка в Program Files), затем ПЕРЕЗАГРУЗКА с подключённым
посторонним накопителем - при входе должно появиться сообщение о его
блокировке; повторное обычное подключение тоже должно уведомлять.

ЭТАП 63. ПОВТОРНЫЕ УВЕДОМЛЕНИЯ ПРИ ЛОГОНЕ - ОДИН РАЗ
--------------------------------------------------
Запрос пользователя: "при логоне, если вставлено устройство не из whitelist,
сообщение о блокировке появляется много раз и перемещается по правому краю

Причина: множество "_reportedLetterless" (диски без буквы, уже уведомлённые)
было статическим на ПРОЦЕСС. Служба и трей - это разные процессы: каждый
запуск трея при входе пользователя писал собственное событие о том же диске
в общую очередь HKLM\SOFTWARE\USB_Block\Events, и при логоне все накопленные
события показывались подряд, и каждый следующий попап ставился выше
(правый край, вверх).

Что сделано в usb_block_tray.cs:
- Учёт "уже уведомлённых дисков без буквы" перенесён из памяти процесса в
  реестр: HKLM\SOFTWARE\USB_Block\ReportedLetterless, значение "Keys"
  (multi-string). Новые функции:
    LoadReportedLetterless() / SaveReportedLetterless(set) /
    AddReportedLetterless(key)
- Scan: после снятия буквы ключ диска теперь добавляется в реестровый набор
  (AddReportedLetterless), а не в устаревшее поле _reportedLetterless.
- AddLetterlessUnallowed: работает с набором из реестра; маркер диска
  удаляется, когда диск исчезает из системы (gone), чтобы повторное
  физическое подключение снова давало уведомление.
- Старое поле _reportedLetterless (static HashSet) удалено.

Поведение теперь: одно событие на одно физическое присутствие диска
(записывает первый процесс - служба или трей), новые входы не дублируют;
повторное подключение того же диска снова уведомляет.

Проверено: csc без ошибок; exe пересобран с трейлером [jpg][длина]"USBICON"
на месте; selftest 4/4 OK (Export/import, сериализация, карта томов - 2 тома,

ЭТАП 64. ИСКЛЮЧЕНЫ ДУБЛИ УСТРОЙСТВ В WHITELIST (ДОБАВЛЕНИЕ И ИМПОРТ)
--------------------------------------------------
Запрос пользователя: "при добавлении в whitelist usb-устройств нужно
исключить дублирование, добавь проверку; так же нужно исключить
дублирование при импорте данных whitelist".

Что было не так:
- проверка при добавлении (DoAddDevice) сравнивала только UsbId+Serial
  "как есть": у одной и той же флешки серийник мог различаться регистром
  или хвостом "&0" от USBSTOR, и запись проходила повторно;
- при импорте с ответом "Да" (замена) список брался из файла КАК ЕСТЬ -
  дедупликация не выполнялась вообще; внутри одного .wlb дубли тоже
  сохранялись;
- "Нет" (объединение) дедуплицировал по строке UsbId|Serial - тот же
  накопитель с другим написанием серийника считался новым;
- дубликаты, попавшие в whitelist.dat раньше, нигде не вычищались.

Сделано в usb_block_tray.cs:
- новый класс WhitelistRules - единственный источник правил whitelist:
    Norm()/NormSerial() - сравнение без учёта регистра, у серийника
      отбрасывается хвост "&0"/"&1f" (как в UsbQuery.ExtractSerial);
    SameDevice(a,b) - "тот же накопитель": серийники равны -> да; если у
      одной записи серийник неизвестен - сравниваются HardwareID диска,
      затем модель USB (VID&PID);
    EntryKey() - ключ записи (первый непустой признак) для HashSet;
    Find() - индекс первой записи о том же накопителе;
    Dedupe(list, out removed) - чистка списка: остаётся ПЕРВАЯ запись,
      ей дописывается имя, если своё пустое; UsbId/Serial/DiskId НЕ
      меняются (иначе изменилось бы то, чем устройство опознаётся);
    Merge(existing, incoming) - объединение: existing имеет приоритет,
      дубликаты отбрасываются в т.ч. внутри каждого списка.
- пункт 3 «Добавить устройство»: поиск дубликата через WhitelistRules.Find
  + подробное сообщение DuplicateMessage (что уже записано: Ім'я пристрою,
  Тип пристрою (ID), Модель пристрою, серийный номер, дата добавления;
  если серийники различаются и совпала только модель - предупреждение, что
  это может быть ДРУГОЙ накопитель, и подсказка удалить старую запись
  пунктом 4).
- пункт 6 «Импорт whitelist»: файл очищается от дублей ПЕРЕД выбором
  действия (в окне сразу видно "Дубликатов в файле отброшено: N"), текущий
  whitelist тоже чистится (в окне - "Дубликатов в текущем whitelist будет
  убрано: N"), и результат не содержит дублей в обоих режимах (замена и
  объединение). Итоговый отчёт DupReport: отброшено в файле / пропущено
  (накопитель уже был в whitelist) / убрано в прежнем списке. Пустой
  файл импорта больше не стирает whitelist ("Файл не содержит ни одного
  устройства - импорт отменён").
- WhitelistStore.Save и PortableWhitelist.Export чистят список от дублей
  сами - гарантия "в файле и в .wlb дублей нет" для любого сценария
  (включая правку старого whitelist.dat).
- пункт 4 «Удалить устройство»: удаление идёт по WhitelistRules.EntryKey,
  поэтому вместе с выбранной записью уходят её дубликаты.
- TrayContext.MergeWhitelists теперь просто вызывает WhitelistRules.Merge
  (своя реализация с ключом UsbId|Serial удалена), сигнатура прежняя -
  используется в --selftest.

Readme.txt: в разделе Whitelist описано правило "один накопитель - одна
запись" (проверка при добавлении, дедупликация при импорте, порядок
сравнения признаков).

Проверено: csc без ошибок; exe пересобран с трейлером [jpg][длина]"USBICON"
(186006 байт) на месте; selftest 6/6 OK - добавились проверки "Dedup add"
(тот же SN в другом регистре и с "&0" и совпавший HardwareID - дубликат;
другая флешка той же модели - нет) и "Dedup import" (3 записи в файле ->
2 после очистки; текущий список с дублем -> 1; после слияния 2).
Контроль на целевой машине: пункт 3 на уже разрешённой флешке - сообщение
"Этот накопитель уже есть в whitelist" без записи; импорт .wlb с дублями -
в отчёте видно, сколько дублей отброшено, в whitelist их нет.

    продолжается;
  * EnsurePassword() - вызывается сразу после EnsureAdmin() в

    DoRemoveService (8), DoUninstall (9). Если пароль не установлен -
    пункт выполняется без запроса. Три попытки, после исчерпания -
    сообщение и отказ. Отмена окна - отказ от выполнения пункта.
- п.9 «Удалить программу»: вопрос о данных теперь «Удалить сохранённые
  данные? - whitelist ... - пароль защиты меню ...» (удаляется вся папка

  файлы остаются.

- Selftest: новая проверка "Password guard" - верный пароль проходит
  PackRecord/CheckPacked, другой регистр и лишний пробел - не проходят,

ЭТАП 68. ОФОРМЛЕНИЕ КОНТЕКСТНОГО МЕНЮ: НЕБЕСНОГОЛУБОЙ ФОН,

Запрос пользователя: "сделай общий фон контекстного меню - небесноголубым,

Почему не через BackColor: WinForms рисует ToolStrip (ContextMenuStrip)

Что сделано в usb_block_tray.cs:

  ToolStripProfessionalRenderer. Цвета: MenuBack = LightSkyBlue
  (135, 206, 250) - общий фон; StatusBack = Yellow (255, 255, 0) - поле
  статуса; BorderColor = Blue (0, 0, 255) - левый бордюр; плюс
  SelectedBack (150, 215, 250) и SelectedLine (0, 90, 158) для
  выделения пункта под курсором. Конструктор принимает ToolStripItem

  зон за разделителями).
- OnRenderToolStripBorder - сначала обычная рамка базового

  рисовал поверх свои градиенты Office-темы.

  RenderMode ставится ПОСЛЕ Renderer - иначе включённый RenderMode

ЭТАП 70. ЖУРНАЛ ПОДКЛЮЧЕНИЙ USB-НАКОПИТЕЛЕЙ И КОПИРОВАНИЙ ФАЙЛОВ
--------------------------------------------------
Задача пользователя: вести журнал - какие накопители подключались и что
копировалось на разрешённые накопители. Смотреть его обычный пользователь
не должен, поэтому сделан отдельный просмотр по горячей клавише.

Принятые решения (уточнены у пользователя):
- журналируются ТОЛЬКО накопители (USBSTOR), обычные диски - нет;
- файлы определяются ОПРОСОМ дерева каталогов (USN/аудит не применялись);
- содержимое файлов, имя пользователя и имя копирующей программы НЕ пишутся
  (только имя файла, размер, время);
- журнал лежит в C:\ProgramData\USB_Block рядом с whitelist.dat;
- шифрование каждой записи DPAPI LocalMachine + закрытый ACL; ключ зашит в
  программу, поэтому смысл ACL - без него шифрование не мешает прочитать;
- просмотр - только по горячей клавише, задаваемой при установке службы;
  отдельного пункта меню нет;
- клавиша должна работать всегда, даже если значок выгружен из трея;
- 10 файлов по 10 000 записей, самые новые - в journal.dat.

Что добавлено в usb_block_tray.cs:
- StorePaths: JournalFile, JournalGenerations (=9), JournalGenerationFile(i).
- UsbJournal: формат "USBJRNL1" + [uint32 длина][шифр] на запись,
  DataProtectionScope.LocalMachine, энтропия зашита в программу,
  ротация поколений, чтение от новых к старым, очистка, счётчик файлов,
  UseDirectoryForTest() для самопроверки.
- UsbJournalMonitor: общий мьютекс Global\UsbBlockJournal_Cycle_v1
  (Local - запасной), присутствие накопителей в реестре
  HKLM\SOFTWARE\USB_Block\JournalPresence (MultiString "ключ TAB описание")
  и метка времени последнего цикла; список файлов тома с лимитами
  200 000 файлов / 1500 мс; пропуск служебных папок и точек монтирования;
  сравнение снимков; эвристика переименования; перерыв > 30 с = новая
  молчаливая отправная точка.
- Виды записей: DEV+ подключение, DEV- отключение, DEV= обнаружено,
  FILE+ скопировано, FILE~ изменён, FILE- удалён, FILE> переименовано, SYS.
- HotkeyStore (HKLM\SOFTWARE\USB_Block\Hotkey) + HotkeyCaptureForm
  (нажать Enter для подтверждения) + HiddenWindow с WM_HOTKEY.
- Клавишу регистрирует трей, а после выгрузки трея - процесс --notify.
- JournalViewForm: три вкладки (Все события / Накопители / Файлы),
  фильтр по тексту, копирование выделенного, сохранение в .txt.
- Program --journal: просмотр в отдельном процессе, при нехватке прав
  запрос повышения (UAC).
- Пункт 7 спрашивает клавишу ПОСЛЕ вопроса про пароль; пункт 8 и
  удаление программы (9) стирают настройку; при установке службы
  показывается всплывающая подсказка с самой комбинацией.
- --diag: блок «Журнал подключений и копирований».

Ошибки и решения (этап 70):
1. Автотест не проходил: Hotkey parse FAIL, мод_как_клавиша=False.
   Причина: в System.Windows.Forms.Keys есть значения-БИТЫ модификаторов -
   Shift = 0x10000, Control = 0x20000, Alt = 0x40000. ShiftKey = 0x10 - это
   ДРУГОЕ число. Enum.Parse("Shift") возвращает 0x10000, проверка его не
   ловила, и "Ctrl+Shift" принималось как готовое сочетание.
   Решение: HotkeyStore.IsMainKey() - основная клавиша это виртуальная
   клавиша 0x01..0xFF, плюс явный запрет Control/Menu/Shift и их
   L/R-вариантов; IsModifierKey() для окна захвата.
2. ACL не применялся к новому journal.dat ПОСЛЕ ротации: признак "файл
   создан" считался ДО RotateIfFull(), а ротация как раз освобождает файл.
   Решение: сначала ротация, потом created = (fs.Length == 0) по уже
   открытому потоку, ACL ставится по этому признаку.
3. Ротация пересчитывала число записей перебором ФАЙЛА на каждую
   запись - при копировании тысяч файлов это квадратичная работа.
   Решение: счётчик в памяти (_count/_countLoaded), CurrentCount(),
   ResetCountForTest(); MaxRecordsPerFile сделан internal - ради проверки.
4. VolumeKey был только по серийному номеру. У накопителя с двумя
   разделами номер общий - второй раздел затирал снимок первого, и в
   журнал шли тысячи ложных "удалён". Решение: в ключ добавлен номер

ЭТАП 71 (продолжение). ГОРЯЧАЯ КЛАВИША: УБРАНО АВТОМАТИЧЕСКОЕ ДОБАВЛЕНИЕ Win
--------------------------------------------------
Задача пользователя: "убери при назначении горячих клавиш просмотра журнала
автоматическое добавление клавиши Win".

Причина (настоящий дефект, а не только неудобство): в HotkeyCaptureForm.
Accept() модификаторы читались из битов keyData, причём Win - так:
    if ((keyData & Keys.LWin) != 0 || (keyData & Keys.RWin) != 0) ...
В System.Windows.Forms.Keys НЕТ отдельного бита-модификатора для Win, поэтому
проверяли по кодам клавиш 0x5B (LWin) и 0x5C (RWin). У этих чисел общие
биты с кодами обычных клавиш: 0x58 & 0x5B = 0x58, 0x5A & 0x5B = 0x5A,
0x43 & 0x5B = 0x43 и т.д. Из-за этого ЛЮБОЕ сочетание с X, C, V, Z, W
(и другими кодами из этого диапазона) записывалось как "...+Win+..." -
пользователь набирал Ctrl+Alt+U или Ctrl+Shift+C, а получал Ctrl+Alt+Win+U.
Win при этом в реальном сочетании может и не быть.

Сделано:
1. Модификаторы берутся из ФИЗИЧЕЧЕСКОГО состояния клавиш - свойства
   ModifierKeys (Keys.Control/Keys.Alt/Keys.Shift: у них есть настоящие
   биты-модификаторы). Смысл: смотрим, что реально зажато, а не разбираем
   битовую маску ключа.
2. Win в сочетаниях для журнала не используется (просьба пользователя).
   В Keys бита для Win нет - состояние клавиш спрашивается напрямую
   через GetKeyState(VK_LWIN=0x5B) / GetKeyState(VK_RWIN=0x5C), берётся
   старший бит ("нажата сейчас"). Если Win зажата, окно показывает
   "Клавиша Win в сочетании для журнала не используется - отпустите её и
   наберите сочетание снова" и НЕ принимает сочетание (иначе на экране
   появилось бы то же самое сочетание без Win - тихое враньё).
3. Подсказки окна приведены в соответствие: "хотя бы один из Ctrl, Alt,
   Shift", "Ctrl, Alt и Shift задаются как добавка", "Клавиша Win не
   используется".
4. HotkeyStore.TryParse "Win+..." оставлен - совместимость: значение,
   сохранённое старой версией (Win туда попадал как раз из-за ошибки выше)
   или вписанное руками, должно зарегистрироваться, а не превратиться в
   "НЕ РАСПОЗНАЁТСЯ". Комментарий об этом добавлен в код.
5. Самопроверка: пункт Hotkey parse дополнен проверкой win_из_старого
   (TryParse("Win+Ctrl+U") -> ModWin и vk=U).

Заодно выправлен блок finally в UsbJournalMonitor.Cycle(): он остался с
сбитыми отступами (оператор в нулевом отступе внутри блока, следующие три
строки - как будто внутри if без фигурных скобок). Поведение было верным,
читаемость нет; отступы и фигурные скобки приведены в порядок, добавил
комментарий про восстановление состояния наблюдения после сбоя цикла.

Первая попытка сборки после правки не прошла из-за моей ошибки:
ModifierKeys - ЭТО СВОЙСТВО (возвращает Keys), а не тип, поэтому
"ModifierKeys.Control" компилятор прочитал как доступ к члену экземпляра
(CS0176), и "ModifierKeys.Windows" не существует (нет такого члена в Keys).
Правильно: (held & Keys.Control) == Keys.Control, а Win - через GetKeyState.

Проверено: csc без ошибок и предупреждений; exe 237717 байт с трейлером
[jpg][uint32 8842][USBICON]; selftest 14/14 OK, строка Hotkey parse:

ЭТАП 72. ИЗ ЖУРНАЛА УБРАНЫ VID:PID (НАКОПИТЕЛИ) И МОДЕЛЬ (ФАЙЛЫ)

Сделано в usb_block_tray.cs:
1. UsbJournalMonitor.DescribeDevice() (записи DEV+/DEV-/DEV=) - поле

   Причина: VID:PID - это идентификатор узла USB, а не свойство накопителя;

   строке каждого файла (а это тысячи строк при копировании) она была
   повтором. Эти методы сделаны internal - их проверяет самопроверка.
3. Самопроверка, пункт "Journal record fields (no VID:PID / no Модель in
   files)": собираются обе строки на тестовых данных и проверяется, что
   VID:PID нет в записи о накопителе, модель есть, а в записи о файле
   модели нет, но SN и Метка есть. У тестового накопителя намеренно не
   задан DiskDeviceId - тогда буква не ищется и WMI не трогается.

Замечание: уже записанные записи не меняются (журнал - append-only, старые
поколения остаются как есть). Новый состав применяется только к новым
записям; если старые строки с VID:PID мешают, журнал можно очистить

ЭТАП 75. ЖУРНАЛ КОПИРОВАНИЯ ПРИ ВХОДЕ ОБЫЧНОГО ПОЛЬЗОВАТЕЛЯ
-------------------------------------------------------------
Задача пользователя: включена галочка «J Вести журнал копирования», но при
входе пользователя БЕЗ прав администратора журнал не пишется.

Причина: программа при входе обычного пользователя правами не повышается
(иначе UAC-вопрос при каждом входе), а RunScan() вызывается только при
Program.IsAdministrator(). Служба мониторинга, которая могла бы вести
журнал, может быть не установлена.

Выбранный пользователем вариант: дописывать в основной журнал (а не в
отдельный файл-очередь). Ротацию файлов по-прежнему оставляем
администратору.

Сделано в usb_block_tray.cs:
1. Дописывание вместо перезаписи файла. Убрано открытие через FileStream
   на запись: теперь CreateFileW с правами
   FILE_APPEND_DATA | FILE_READ_ATTRIBUTES. Windows сама ставит указатель
   в конец файла, поэтому указатель перед Position=0 «как было» больше не
   нужен и переписать/стереть уже записанное нельзя. Отдельная функция
   AppendBytes(), кадр собирает BuildFrame().
2. Сбой ACL: файлы журнала закрывались ACL только на администраторов и
   SYSTEM (RestrictDirectoryAcl/RestrictAcl). Добавлен класс
   UsbJournalRights:
   - EnsureFileRights() - админам и SYSTEM полный доступ, обычному
     пользователю (Authenticated Users) Read | AppendData;
   - EnsureAllFileRights() - то же для всех 10 поколений (файлы прежних
     версий);
   - EnsureAllOnce() - один раз на процесс при запуске администратора;
   - CanWriteNow() - проверка «умеем ли мы писать» для --diag и трея;
   - EnsurePresenceRights() - ключу HKLM\SOFTWARE\USB_Block\JournalPresence
     дано SetValue | ReadKey | CreateSubKey для обычного пользователя
     (RegSetKeySecurity по DACL). CreateSubKey нужен потому, что код
     открывает ключ через Registry.CreateSubKey: на существующем ключе это
     право проверяется, без него метка последнего цикла не писалась бы;
   - EnsureWhitelistRead() - обычному пользователю Read на whitelist.dat.
3. WhitelistStore.Save() больше не зовёт RestrictAcl (он снимал бы и
   право на чтение): вместо него EnsureWhitelistRead(). Без чтения
   whitelist список разрешённых выглядел бы пустым, и обычный пользователь
   отметил бы чужие накопители удалёнными.
4. Владелец цикла (решает проблему «оба процесса пишут по очереди»).
   Мьютекс запрещает идти одновременно, но не запрещает по очереди. В
   JournalPresence добавлены Owner и OwnerTicks; TryClaimOwner() сравнивает
   метку с MaxGap (30 с): метка свежая и чужая - молчим; метки нет или она
   протухла - забираем себе; служба забирает журнал у трея, трей у службы
   - нет; метка из будущего (часы переведены назад) - тоже уступаем, иначе
   после правки времени пошёл бы поток ложных «удалено». Смена владельца
   сбрасывает _primed, чтобы не наследить. Проверка владельца перенесена
   ПОД мьютекс (иначе оба успевали увидеть «владельца нет»).
   Тестовая подмена: UseOwnerForTest(), TryClaimOwnerForTest();
   токен в тестовом режиме считается на каждый вызов, иначе проверка
   приоритета ничего не проверяла бы.
5. SaveLastCycle(now, privileged) и метка в памяти: обычный пользователь
   пишет метку последнего цикла (иначе он считал бы каждый свой цикл
   «первым после перерыва» и молчал). Если запись в реестр не вышла -
   метка держится в памяти процесса (_lastCycleMemoryOnly), и NeedsReba-
   seline доверяет ей.
6. Ротация при заполненном файле по-прежнему только администраторская, но
   теперь это видно: RotateIfFull() возвращает bool, и если сдвинуть
   поколения нечем, запись прекращается с явным текстом в UsbJournal.
   LastError и всплывающим сообщением в трее («файл журнала заполнен…»),
   а не молча пишет сверх 5 000.
7. Трей обычного пользователя теперь всё же ходит в журнал: RunJournalOnly()
   в таймере (RunScan() по-прежнему только под администратором), плюс
   CheckJournalWritable() - одно всплывающее сообщение, если журнал
   включён, а писать нечем.
8. --diag: «Право дописывать в журнал у этого процесса», «запись
   невозможна: …», «журнал ведёт другой процесс: …», «ошибка выдачи прав».
9. Самопроверка +2 строки (было 17, стало 19):
   - "Journal append-only" - дописывание работает, начало файла не
     изменилось, и в ACL файла для пользователя есть AppendData, но нет
     Write/Delete. Права читаются из ACL файла, а не из попытки записи:
     иначе результат зависел бы от того, под чем запущена самопроверка. Если
     прав ещё нет и самопроверка идёт без прав администратора - строка
     печатается как "OK (ждём прав администратора)", это не поломка;
   - "Journal owner" - трей не отбирает журнал у живой службы, служба
     отбирает у трея, трей забирает после молчания и держит свой,
     метка из будущего уступается.
   Исправлено попутно: при создании файла заголовок формата писался и
   возвращал управление, не записав кадр, - первая запись в новый файл
   терялась.

Проверено: csc без ошибок и предупреждений; exe 331925 байт с трейлером
USBICON на месте; selftest 19/19 OK, в том числе
